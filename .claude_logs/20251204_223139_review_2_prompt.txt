## Service Specification
# Service Specification: redirect-service

## Overview

The `redirect-service` is a high-performance URL redirect service optimized for ultra-low latency. It accepts HTTP requests containing short codes and performs HTTP 301 redirects to the original long URLs. The service prioritizes read performance through aggressive caching strategies, utilizing Redis as the primary data source with PostgreSQL read replicas as fallback. It is designed to handle 10,000+ requests per second with p99 latency under 50ms.

**Key Characteristics:**
- Read-optimized microservice (no write operations)
- Cache-first architecture with >95% cache hit rate target
- Horizontally scalable via Cloud Run
- Higher availability priority than shortening service
- Minimal resource footprint (256Mi memory, 1 vCPU)

## APIs/Interfaces

### GET /{shortCode}

**Description:** Redirects the user to the original long URL associated with the provided short code. This is the primary endpoint and handles 99%+ of all traffic to this service.

**Path Parameters:**
- `shortCode` (string, required): 6-8 character alphanumeric identifier (base62 encoded)

**Request:**
```http
GET /aB3xY9 HTTP/1.1
Host: short.link
User-Agent: Mozilla/5.0
Accept: text/html
```

**Response (301 Moved Permanently):**
```http
HTTP/1.1 301 Moved Permanently
Location: https://example.com/very/long/url/path?query=params
Cache-Control: public, max-age=300
X-Request-ID: req-abc123xyz
X-Cache-Status: HIT
Content-Length: 0
```

**Response (404 Not Found):**
```http
HTTP/1.1 404 Not Found
Content-Type: application/json
X-Request-ID: req-abc123xyz
X-Cache-Status: MISS

{
  "error": "not_found",
  "message": "Short code not found",
  "short_code": "invalid1"
}
```

**Response (400 Bad Request):**
```http
HTTP/1.1 400 Bad Request
Content-Type: application/json
X-Request-ID: req-abc123xyz

{
  "error": "invalid_short_code",
  "message": "Short code must be 6-8 alphanumeric characters",
  "short_code": "ab@#$"
}
```

**Response (500 Internal Server Error):**
```http
HTTP/1.1 500 Internal Server Error
Content-Type: application/json
X-Request-ID: req-abc123xyz

{
  "error": "internal_error",
  "message": "Unable to process redirect request",
  "request_id": "req-abc123xyz"
}
```

**Response (503 Service Unavailable):**
```http
HTTP/1.1 503 Service Unavailable
Content-Type: application/json
Retry-After: 30
X-Request-ID: req-abc123xyz

{
  "error": "service_unavailable",
  "message": "Service temporarily unavailable",
  "retry_after": 30
}
```

**Business Logic:**

**Happy Path (Cache Hit - 95%+ of requests):**
1. Extract `shortCode` from URL path (e.g., `/aB3xY9` → `aB3xY9`)
2. Validate short code format (6-8 alphanumeric characters, base62)
3. Construct Redis key: `url:aB3xY9`
4. Execute Redis GET operation (1-2ms typical)
5. If value exists in cache:
   - Parse long URL from Redis value
   - Return HTTP 301 redirect with `Location` header
   - Include `X-Cache-Status: HIT` header
   - Log request with cache hit metric
   - **Total latency: 3-5ms**

**Sad Path (Cache Miss - <5% of requests):**
1. Extract and validate `shortCode` as above
2. Construct Redis key: `url:aB3xY9`
3. Execute Redis GET operation (1-2ms)
4. Cache miss detected
5. Query PostgreSQL read replica:
   ```sql
   SELECT long_url FROM url_mappings WHERE short_code = $1;
   ```
6. If row found in database:
   - Store result in Redis with TTL: `SET url:aB3xY9 {longUrl} EX 3600`
   - Return HTTP 301 redirect with `Location` header
   - Include `X-Cache-Status: MISS` header
   - Log request with cache miss metric
   - **Total latency: 15-20ms**
7. If row not found in database:
   - Return HTTP 404 Not Found
   - Include error details in JSON response
   - Log 404 event
   - **Do not cache negative results** (prevents cache pollution)

**Edge Cases:**

**Case 1: Invalid Short Code Format**
- Input: `/ab@#$` or `/toolongshortcode123`
- Validation: Regex check `^[a-zA-Z0-9]{6,8}$`
- Response: HTTP 400 Bad Request
- Action: Return error immediately without cache/DB lookup
- Latency: <1ms

**Case 2: Redis Connection Failure**
- Scenario: Redis unavailable or timeout
- Fallback: Skip cache, query PostgreSQL directly
- Response: HTTP 301 if found, HTTP 404 if not found
- Action: 
  - Log Redis failure with ERROR severity
  - Increment `redis_connection_errors_total` metric
  - Do not cache result (Redis unavailable)
  - Alert on-call if error rate exceeds threshold
- Latency: 10-15ms (DB query only)

**Case 3: PostgreSQL Connection Failure**
- Scenario: Database unavailable or timeout
- Response: HTTP 503 Service Unavailable with `Retry-After: 30`
- Action:
  - Log database failure with ERROR severity
  - Increment `db_connection_errors_total` metric
  - Return retry-after header for client backoff
  - Trigger critical alert
- Latency: Timeout threshold (5 seconds)

**Case 4: Both Redis and PostgreSQL Unavailable**
- Scenario: Complete data layer failure
- Response: HTTP 503 Service Unavailable
- Action:
  - Log catastrophic failure
  - Trigger critical alert to page on-call
  - Health check endpoint will fail
  - Cloud Run will attempt to restart instances
  - Load balancer will route to healthy instances

**Case 5: Empty Short Code**
- Input: `/` (root path)
- Response: HTTP 404 Not Found (no redirect service owns root)
- Action: Let load balancer handle root path routing

**Case 6: Malformed URL in Database**
- Scenario: Database contains invalid URL (data corruption)
- Detection: URL validation before redirect
- Response: HTTP 500 Internal Server Error
- Action:
  - Log data integrity error with ERROR severity
  - Increment `data_integrity_errors_total` metric
  - Do not cache corrupted data
  - Alert for manual investigation

**Case 7: Extremely Long URL in Database**
- Scenario: Long URL exceeds HTTP header size limits (8KB typical)
- Response: HTTP 500 Internal Server Error
- Action:
  - Log oversized URL error
  - Return generic error to client
  - Alert for data cleanup

**Case 8: High Concurrency for Same Short Code**
- Scenario: Viral link causes 1000s of simultaneous requests
- Optimization: Redis handles concurrent reads efficiently
- Response: All requests receive HTTP 301 from cache
- Action: Monitor cache hit rate (should remain >99%)

**Case 9: Cache Stampede (Cache Miss Under Load)**
- Scenario: Popular URL expires from cache, 100s of requests hit simultaneously
- Mitigation: Single-flight pattern (only one goroutine queries DB)
- Implementation:
  ```go
  // Use singleflight.Group to deduplicate concurrent requests
  result, err := g.Do(shortCode, func() (interface{}, error) {
      return queryDatabase(shortCode)
  })
  ```
- Response: All concurrent requests wait for single DB query, then receive result
- Action: First request populates cache, subsequent requests hit cache

**Case 10: Expired Cache Entry**
- Scenario: Redis TTL expires (after 3600 seconds)
- Response: Cache miss, query database, repopulate cache
- Action: Normal cache miss flow
- Optimization: Popular URLs remain cached due to frequent access

## Data Model

### Entity: url_mappings (Read-Only Access)

The redirect service has **read-only access** to the `url_mappings` table via PostgreSQL read replica. It does not perform any write operations.

| Field | Type | Constraints | Description |
|-------|------|-------------|-------------|
| id | BIGSERIAL | PRIMARY KEY | Auto-incrementing unique identifier |
| short_code | VARCHAR(8) | UNIQUE NOT NULL | 6-8 character alphanumeric short code (base62) |
| long_url | TEXT | NOT NULL | Original URL to redirect to (max 2048 characters) |
| created_at | TIMESTAMP WITH TIME ZONE | NOT NULL, DEFAULT NOW() | Timestamp when mapping was created |
| created_by_ip | INET | NULL | IP address of client who created the mapping (optional) |

**Indexes:**
```sql

CREATE INDEX idx_created_at ON url_mappings(created_at DESC);
```


**Write (Cache Population):**

## Business Logic Specifications

### Short Code Validation

**Purpose:** Ensure short code meets format requirements before processing

**Algorithm:**
```go
func validateShortCode(code string) error {
    // Length check
    if len(code) < 6 || len(code) > 8 {
        return ErrInvalidShortCodeLength
    }
    
    // Character set check (base62: a-zA-Z0-9)
    matched, _ := regexp.MatchString(`^[a-zA-Z0-9]+$`, code)
    if !matched {
        return ErrInvalidShortCodeCharacters
    }
    
    return nil
}
```

**Error Cases:**
- Empty string → `invalid_short_code`
- Too short (<6 chars) → `invalid_short_code`
- Too long (>8 chars) → `invalid_short_code`
- Invalid characters → `invalid_short_code`

**Performance:** <0.1ms per validation

### Cache Lookup Strategy

**Purpose:** Retrieve long URL from Redis with fallback to database

**Algorithm:**
```go
func getLongURL(ctx context.Context, shortCode string) (string, error) {
    // Step 1: Validate short code
    if err := validateShortCode(shortCode); err != nil {
        return "", err
    }
    
    // Step 2: Construct Redis key
    cacheKey := fmt.Sprintf("url:%s", shortCode)
    
    // Step 3: Attempt Redis lookup
    longURL, err := redisClient.Get(ctx, cacheKey).Result()
    if err == nil {
        // Cache hit
        metrics.CacheHits.Inc()
        return longURL, nil
    }
    
    // Step 4: Handle Redis errors
    if err != redis.Nil {
        // Redis connection error, not just cache miss
        logger.Error("redis_error", zap.Error(err))
        metrics.RedisErrors.Inc()
        // Continue to database fallback
    }
    
    // Step 5: Cache miss - query database
    metrics.CacheMisses.Inc()
    longURL, err = queryDatabase(ctx, shortCode)
    if err != nil {
        return "", err
    }
    
    // Step 6: Populate cache (fire-and-forget)
    go func() {
        ctx, cancel := context.WithTimeout(context.Background(), 1*time.Second)
        defer cancel()
        _ = redisClient.Set(ctx, cacheKey, longURL, 3600*time.Second).Err()
    }()
    
    return longURL, nil
}
```

**Cache Hit Path:**
1. Validate short code (0.1ms)
2. Redis GET (1-2ms)
3. Return result (total: ~3ms)

**Cache Miss Path:**
1. Validate short code (0.1ms)
2. Redis GET returns nil (1-2ms)
3. Database query (5-10ms)
4. Async cache population (1-2ms, non-blocking)
5. Return result (total: ~15ms)

**Error Handling:**
- Redis timeout → fallback to database
- Redis connection refused → fallback to database
- Database timeout → return 503
- Database not found → return 404

### URL Validation (Pre-Redirect)

**Purpose:** Validate long URL retrieved from database before redirecting

**Algorithm:**
```go
func validateLongURL(url string) error {
    // Length check
    if len(url) == 0 || len(url) > 2048 {
        return ErrInvalidURLLength
    }
    
    // Scheme check
    if !strings.HasPrefix(url, "http://") && !strings.HasPrefix(url, "https://") {
        return ErrInvalidURLScheme
    }
    
    // Parse URL
    parsed, err := url.Parse(url)
    if err != nil {
        return ErrMalformedURL
    }
    
    // Host check
    if parsed.Host == "" {
        return ErrMissingHost
    }
    
    return nil
}
```

**Error Cases:**
- Empty URL → `data_integrity_error` (log and alert)
- Missing scheme → `data_integrity_error`
- Invalid characters → `data_integrity_error`
- Missing host → `data_integrity_error`

**Action on Validation Failure:**
- Log error with ERROR severity
- Increment `data_integrity_errors_total` metric
- Return HTTP 500 to client
- Trigger alert for manual investigation
- **Do not cache invalid URLs**

### Request Timeout Handling

**Timeout Configuration:**
```go
const (
    RedisTimeout    = 1 * time.Second   // Redis operations
    DatabaseTimeout = 5 * time.Second   // Database queries
    RequestTimeout  = 10 * time.Second  // Overall request
)
```

**Implementation:**
```go
func handleRedirect(w http.ResponseWriter, r *http.Request) {
    // Create request context with timeout
    ctx, cancel := context.WithTimeout(r.Context(), RequestTimeout)
    defer cancel()
    
    // Extract short code
    shortCode := chi.URLParam(r, "shortCode")
    
    // Get long URL with context
    longURL, err := getLongURL(ctx, shortCode)
    if err != nil {
        if ctx.Err() == context.DeadlineExceeded {
            // Timeout occurred
            respondError(w, http.StatusGatewayTimeout, "request_timeout")
            return
        }
        // Handle other errors
        handleError(w, err)
        return
    }
    
    // Perform redirect
    http.Redirect(w, r, longURL, http.StatusMovedPermanently)
}
```

### Graceful Shutdown

**Purpose:** Drain in-flight requests before terminating

**Algorithm:**
```go
func gracefulShutdown(server *http.Server) {
    // Listen for SIGTERM from Cloud Run
    sigChan := make(chan os.Signal, 1)
    signal.Notify(sigChan, syscall.SIGTERM, syscall.SIGINT)
    
    <-sigChan
    logger.Info("shutdown signal received")
    
    // Stop accepting new requests
    ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
    defer cancel()
    
    // Wait for in-flight requests to complete
    if err := server.Shutdown(ctx); err != nil {
        logger.Error("shutdown error", zap.Error(err))
    }
    
    // Close database connections
    dbPool.Close()
    
    // Close Redis connections
    redisClient.Close()
    
    logger.Info("shutdown complete")
}
```

**Shutdown Sequence:**
1. Receive SIGTERM signal (Cloud Run sends 10s before kill)
2. Stop accepting new requests
3. Wait up to 30s for in-flight requests to complete
4. Close database connection pool
5. Close Redis connection pool
6. Exit process

## Architecture Guidelines
# Architecture: URL Shortener Service

## Goal

Design a high-performance, scalable URL shortening system that prioritizes low-latency redirects and reliable URL shortening. The architecture follows microservices principles with separate services for write operations (URL shortening) and read operations (redirects) to optimize for the read-heavy traffic pattern. The system leverages caching extensively to meet aggressive latency requirements and uses GCP managed services for scalability and reliability.

### Short Code Generation Algorithm

**Approach**: Snowflake-inspired distributed ID generation + Base62 encoding

```
Components:
- Timestamp (41 bits): Milliseconds since epoch
- Worker ID (10 bits): Cloud Run instance identifier
- Sequence (12 bits): Counter for same millisecond

Result: 63-bit unique integer → Base62 encode → 6-8 character string
```

**Base62 Character Set**: `0-9a-zA-Z` (62 characters)

```sql
    -- Indexes

CREATE INDEX idx_created_at ON url_mappings(created_at DESC);
```

### Caching Strategy

**Cache Structure** (Redis):
```
Key: "url:{shortCode}"
Value: "{longUrl}"
TTL: 3600 seconds (1 hour)
```

**Cache-Aside Pattern**:
1. Check Redis for `url:{shortCode}`
2. If found (cache hit): Return URL and redirect
3. If not found (cache miss):
   - Query PostgreSQL read replica
   - If found: Store in Redis with TTL, then redirect
   - If not found: Return 404

**Cache Warming**: Most popular URLs stay cached due to access frequency

**Cache Invalidation**: Handled by shortening-service (not required for current scope)

### Read Flow Optimization

```
Request → Parse shortCode (0.1ms)
       → Redis GET (1-2ms typical)
       → [Cache Hit 95%+] → Redirect (total: ~3-5ms)
       → [Cache Miss 5%-] → PostgreSQL Query (5-10ms)
                          → Redis SET (1-2ms)
                          → Redirect (total: ~15-20ms)
```

**Phase 2: Service Deployment**
1. Deploy shortening-service to Cloud Run (staging)

4. Deploy to production with traffic split (10% → 50% → 100%)

**Phase 3: Monitoring & Optimization**
1. Validate metrics and alerts
2. Load testing
3. Performance tuning
4. Cache warming
